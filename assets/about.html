About This Project

A real-time signal-processing and monitoring system, built in Rust

Every machine has sensors. This system reads signals from those sensors, instantly analyses them, and warns about a failure before it happens - several times faster than existing Python solutions. The state of the machine is reflected both on physical LED indicators and on the live dashboard, forming a real Digital Twin.

Why a Digital Twin, and not something simpler?

The term "Digital Twin" gets used loosely for all kinds of connected dashboards. There are actually three distinct system types, and the difference between them is what this project is really built around:

  • Digital model - a static, offline representation (e.g. a CAD model) with no live data connection at all. Nothing updates automatically in either direction.
  • Digital shadow - a live, one-directional data feed from the physical object into the digital model. Sensors push state in, so the model always reflects current conditions - but the model cannot act back on the physical object. Most "IoT dashboards" are actually this.
  • Digital twin - a live, bidirectional system: sensors feed the model, the model computes a decision (here, an anomaly detection result), and that decision is sent back to physical outputs - the LED bank and buzzer, in this system's case.

That closed loop - sensor data in, a computed decision back out to a physical indicator - is what actually qualifies this as a Digital Twin rather than just a nicer dashboard.

The research question

The thesis behind this project asks a specific, testable question: can a signal-processing pipeline written in Rust - a systems language with compile-time memory safety and no garbage collector - match or beat the throughput of Python's NumPy/SciPy stack on identical workloads, while keeping the kind of predictable, low-jitter timing that a real-time control loop needs? The core of that pipeline is a Fast Fourier Transform, used to turn a motor's vibration signal into a frequency spectrum where developing faults show up as new or shifting frequency components, long before the fault is visible any other way.

Where things stand right now

Both the MPU6050 (motion) and the BME280 (temperature, humidity, pressure) are live, real sensor data, each running on its own independent I2C bus. This replaces an earlier DHT22 sensor, which worked perfectly on its own but proved unreliable whenever the Wi-Fi radio was active - an extensively investigated and documented hardware-coexistence issue (see tech.md for the full write-up). I2C's clock line gives it real tolerance for exactly the kind of disruption that broke the DHT22's single-wire, self-timed protocol. The LED/buzzer classification logic has been validated against all 9 possible green/yellow/red combinations, and the "Simulate" page remains available for testing/demo purposes.
